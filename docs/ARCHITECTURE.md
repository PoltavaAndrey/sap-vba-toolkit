# Архитектура

## Принципы

1. **Один класс - одна ответственность.**
   - `clsSapConnector` только устанавливает соединение с SAP GUI.
   - `clsSapSession` только оперирует элементами управления внутри уже
     полученной сессии.
   - `clsExcelReader` / `clsExcelWriter` разделены по направлению
     (чтение / запись), т.к. это разные жизненные циклы и разные наборы
     операций.
   - `clsLogger` не знает ничего о SAP или Excel - только пишет строки лога.

2. **Интерфейсы через `Implements`.**
   Логирование спрятано за интерфейсом `ILogger`. Это позволяет:
   - подменить реализацию (например, добавить `clsDbLogger`,
     `clsTeamsLogger`) без изменения кода, который логирует события;
   - в модульных тестах подставлять "заглушку"-логгер.

3. **Явная инициализация вместо конструктора с параметрами.**
   В VBA у классов нет конструкторов, принимающих параметры (только
   `Class_Initialize` без аргументов). Поэтому используется паттерн
   `New ClassName` + `.Init(...)`, где `Init` играет роль конструктора и
   передает зависимости (Dependency Injection в упрощенном виде).

4. **Фасад (`clsAppController`) как единственная точка сборки.**
   Только `clsAppController.Init` создает конкретные реализации
   (`New clsLogger`, `New clsSapConnector` и т.д.). Все остальные части
   кода получают уже готовые объекты через параметры или свойства и не
   зависят от того, как именно они были созданы.

5. **Позднее связывание (`CreateObject`, `As Object`).**
   Все внешние COM-объекты (SAP GUI, второй экземпляр Excel) объявлены как
   `Object`, а не через конкретные библиотеки типов. Это убирает
   необходимость подключать ссылки VBA (`Tools -> References`) на стороне
   каждого пользователя и снижает риск ошибок из-за разных версий
   SAP GUI/Excel на разных машинах.

## Диаграмма зависимостей (текстовая)

```
modMain
  -> clsAppController
       -> ILogger (clsLogger)
       -> clsSapConnector
            -> clsSapSession
       -> clsExcelReader
       -> clsExcelWriter
```

Стрелка "->" означает "использует / зависит от". Обратных зависимостей
(например, чтобы `clsSapSession` знал про `clsExcelWriter`) в проекте
намеренно нет - это удерживает классы независимыми и переиспользуемыми.

## Обработка ошибок

- Каждый публичный метод, выполняющий потенциально нестабильную операцию
  (обращение к SAP, файлам, Excel), обернут в `On Error GoTo ErrHandler`.
- Ошибки логируются с номером и описанием (`Err.Number`, `Err.Description`)
  и, там где это осмысленно, метод возвращает `Boolean` (успех/неуспех),
  а не прерывает выполнение всего макроса.
- `Class_Terminate` у `clsLogger`, `clsExcelReader`, `clsExcelWriter`
  подчищает ресурсы (закрывает файлы, завершает временные экземпляры
  Excel), даже если вызывающий код забыл сделать это явно.

## Возможные направления развития

- Вынести структуру входного файла (имена столбцов) в конфигурацию,
  а не хардкодить внутри `clsAppController`.
- Добавить `clsSapTable` для работы с табличными контролами SAP
  (`GuiTableControl`, ALV Grid) - в текущей версии не реализовано.
- Добавить модуль модульных тестов (например, на базе `Rubberduck VBA`)
  с моками для `ILogger`.
